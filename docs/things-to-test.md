# Things to test

*Started 2026-10-09. What Claude isn't sure about in each project, and the test that would settle it.*

**Read this before every test spec.** When a spec is about to be released, look at its project's section and add the open items it can cover cheaply, so each round of generation answers more than one question.

## How it works

1. **Before a release:** pick the items the spec can cover, and write "covered by CAI0x" in them.
   - Keep a fix check clean: a spec that tests a fix changes only that fix's inputs. Paths that were never built can share a spec, because each kit is checked against its own prediction.
   - Check the release for side effects first (emails, SQL, group tables: [formats/simulation.md](formats/simulation.md#layer-2-the-driveworks-api-on-this-pc)).
2. **After the build:** run the checks:
   - `Test-DwHopperV2Build -Spec <spec copy> -Spa CAI0x`, for what was built;
   - `Get-DwGenerationIssue CAI0x`, for DriveWorks' generation log.

   Then file the bundle with `Move-DwSpa CAI0x` ([formats/spa.md](formats/spa.md#where-the-files-go)).
3. **Record the result** in the item, with the date.
   - A settled item moves to **Settled**, and its finding goes to the project's `learnings.md` or an issue (`tracking/items.json`).
   - A new doubt gets an item here, with how to test it.

**Who does each test:**
- **SW:** the user opens a file from a build in SOLIDWORKS. No new spec is needed.
- **Claude:** offline or through the API. No SOLIDWORKS is needed.
- **Spec:** a new test spec (prefix CAI, Dev Release on), generated by the user.
- **Prod:** needs data that exists only in production. The user reads it.
